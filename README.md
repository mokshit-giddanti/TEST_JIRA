# JIRA & BCS Hours Tracker

A modern web application for managing sprint JIRAs, Story Points and BCS hour bookings. Built with **Flask + SQLAlchemy + PostgreSQL** and prepared for deployment on **Render**.

## Features

- Master JIRA tracker: **Sprint, JIRA, Story Points, Days/Hours, Bookings**.
- Automatic conversions: **1 Story Point = 0.5 Day = 4 Hours; 1 Day = 8 Hours**.
- **Add New JIRA Row** button with a separate booking detail page for each JIRA.
- **Add New Booking Row** with editable date (defaults to today's local date), hours and remarks.
- Running remaining-hours calculation: **Total Hours − cumulative booked hours**.
- Edit/delete records, searchable/filterable master table, workload summary cards.
- **Download Excel** for the complete tracker (master + separate sheet for each JIRA).
- **Export this JIRA** for a single JIRA.
- Optional workspace password; Render configuration requires one.
- Durable PostgreSQL data storage on Render; SQLite is for local development only.

## Deploy to Render (recommended: Blueprint)

1. Create a new **private GitHub repository** and upload all files and folders from this project, including `render.yaml`.
2. Sign in to [Render](https://dashboard.render.com/), click **New → Blueprint**, and connect that GitHub repository.
3. Render will read `render.yaml` and propose the Python web service and PostgreSQL database.
4. Supply a **strong ADMIN_PASSWORD** when Render asks for it. Render will generate a `SECRET_KEY` and connect `DATABASE_URL` automatically.
5. Approve the Blueprint and wait for deployment. Open the `https://<service-name>.onrender.com` link and sign in.
6. Add JIRAs from the app, log bookings, and click **Download Excel** whenever you need a workbook.

### Critical: Free Render Postgres expires

The supplied Blueprint uses `plan: free` for both the web service and PostgreSQL, suitable for testing. **Render's free PostgreSQL databases expire after 30 days**. To retain important data beyond the free trial, **upgrade the database to a paid plan before it expires**, or export and back up your data and plan a new persistent datastore. The free web service may sleep after inactivity. Render web-service filesystems are ephemeral: do not use local SQLite as the live hosted database.

If you prefer a paid durable database from the start, change the `databases` section to `plan: 0.1c-256mb` before deploying (subject to current Render pricing).

## Local development

Install Python 3.11+:

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows: .venv\Scripts\activate
pip install -r requirements.txt
python app.py
```

Open http://127.0.0.1:5000. The local database is `instance/jira_bcs_local.db`. To enable a password locally, set environment variable `ADMIN_PASSWORD` before running. `SECRET_KEY` should also be set to a long random value when using login.

### Environment variables

| Variable | Meaning |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string on Render; local fallback: SQLite |
| `SECRET_KEY` | Cryptographic Flask session key; automatically generated by Render Blueprint |
| `ADMIN_PASSWORD` | Password protecting all app data and Excel downloads |
| `PORT` | Provided automatically by Render; 5000 locally |

## Application storage

- `jiras` holds each JIRA's unique record ID, sprint, JIRA code and story points.
- `bookings` holds each booking's date, BCS hours, remark and its parent JIRA record ID.
- Because bookings reference the stable internal JIRA ID, editing a JIRA code keeps its existing booking history.
- Remaining hours use booking date followed by creation timestamp, so dated historical entries are recalculated chronologically.

## Excel download contents

- `Master Tracker`: Sprint, JIRA, Story Points, Days, Total Hours, Bookings link.
- One sheet per JIRA: Total Hours, Date, Booking Hours for BCS, Remark for BCS, Remaining Hours.
- Styled tables, frozen headers, date formatting, and hyperlinks from the master to each JIRA sheet.

## Security and scope

This starter project provides a **single shared password**; it is designed for a personal/private work tracker, not a multi-user enterprise timesheet system. Use a strong password and keep it out of your repository. For multiple employees or sensitive organizational data, extend it with named user accounts, permissions, audit history and backups before use. Do not upload confidential work information without the appropriate company approval.
